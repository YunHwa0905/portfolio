Overview

프로젝트 개요

Problem
법률 용어가 어려워 일반인의 법률 접근성이 낮고, 전문가 상담 비용 부담이 크다는 문제에서 출발했습니다.
Solution
AIHub 법률 문서(법령·판결문·유권해석·결정례·심결문) 253,207건을 전처리해 OpenSearch 기반 RAG 검색을 구성하고, 가입 시 입력한 나이로 설명 난이도 4단계를 기본 설정해 눈높이에 맞는 답변을 제공하는 법률 AI 상담 서비스를 개발했습니다.

Architecture

아키텍처

  • 3-Tier 구조: Express(Frontend) → Spring(JWT 인증) → FastAPI(RAG 검색·추론) → OpenSearch + MySQL
  • Oracle Cloud(Ubuntu 24.04) 한 대에 Frontend(3000)·Spring(8181)·FastAPI(8000)·OpenSearch(9200)·Ollama(11434)·MySQL(3306)을 포트로 분리 배포
  • OpenSearch legal_documents 인덱스(text·source·embedding 필드)에서 kNN과 BM25를 각각 별도 쿼리로 실행한 뒤, 점수를 max 정규화하여 가중 합산(kNN 1.0 : BM25 0.5)하는 하이브리드 검색
  • MySQL users 테이블의 age를 JWT에 담아 FastAPI로 전달, 설명 난이도 4단계로 분기
  • Spring Boot(JPA·Security) 버전과 Spring Legacy(MyBatis·수동 Filter) 버전을 각각 구현해 비교

Problem Solving

문제 해결 과정

검색 정확도 — BM25와 kNN 단독의 한계

🚨 문제
BM25 단독은 "해약 절차"↔"계약 해지"처럼 유사한 표현을 찾지 못했고, kNN 단독은 법률 용어의 정확한 매칭이 떨어졌습니다.
🔍 원인
한국어 형태소 분석기(nori) 없이 standard analyzer로 색인해 조사·어미 처리가 안 되다 보니 BM25 품질에 한계가 뚜렷했고, kNN만으로는 정확한 법률 용어 매칭이 약했습니다.
🛠 해결
kNN과 BM25를 각각 별도 쿼리로 실행해 점수를 max 정규화한 뒤 가중 합산했습니다(kNN 1.0 : BM25 0.5). BM25 쿼리 내부에서는 본문 필드(text)에 2배 부스트를 적용했습니다.
✅ 결과
253,207건(4개 법률 분야)에서 키워드·의미 검색을 동시에 확보하는 하이브리드 검색으로 최종 채택했습니다. 형태소 분석기 도입은 다음 개선 과제로 남겨뒀습니다.

RAG 컨텍스트 오염 제거

🚨 문제
검색된 문서를 그대로 LLM 컨텍스트에 넣었더니, 원본 데이터의 질문 문장이나 조회수 표기 같은 노이즈가 답변에 섞여 들어갔습니다.
🔍 원인
원본 데이터가 "Q: 질문\nA: 답변" 형태로 저장돼 있어, 검색된 문서 안의 질문 줄과 "_PAGEVIEW_COUNT_" 같은 메타 텍스트가 그대로 컨텍스트에 포함됐습니다.
🛠 해결
"Q:"로 시작하는 줄은 건너뛰고, "_PAGEVIEW_COUNT_"를 비롯한 노이즈 패턴을 필터링하는 후처리 로직을 검색 결과 파싱 단계에 추가했습니다.
✅ 결과
LLM에 전달되는 컨텍스트에서 질문 문장·메타데이터 노이즈를 제거해 답변 품질을 개선했습니다.

LLM 선택 — EXAONE 파인튜닝을 포기하고 Gemma로 전환한 이유

🚨 문제
1주 기한 안에서 EXAONE 3.5 7.8B를 QLoRA로 파인튜닝해 GGUF 변환·Ollama 서빙까지 시도했는데, 6가지 문제(레이어 설정 누락, 텐서 누락, 비정상 GGUF 생성 등)를 모두 해결한 뒤에도 답변 품질이 서비스에 쓸 수 없는 수준이었습니다.
🔍 원인
전체 25만 건 중 1주 기한상 분야별 균등 샘플링으로 4천 건만 학습에 사용했고, 이 학습량 부족이 품질 미달의 주원인이라고 판단했습니다. GGUF 변환 과정에서 config.json의 model_type을 llama로 패치한 것도 instruction-following 성능 저하에 영향을 준 것으로 보입니다.
🛠 해결
"GGUF를 실행 가능하게 만드는 것"과 "서비스에 쓸 수 있는 품질을 확보하는 것"은 별개의 문제라고 판단해, 1주 기한 안에서 이미 검증된 base 모델 Gemma 3 4B로 방향을 전환했습니다. Ollama 레지스트리에서 받은 게 아니라, 로컬에 내려받은 Q8_0 GGUF 파일을 Modelfile로 직접 등록해 서빙했습니다.
FROM ./google_gemma-3-4b-it-Q8_0.gguf PARAMETER temperature 0.1 PARAMETER top_p 0.9 PARAMETER num_ctx 4096 PARAMETER repeat_penalty 1.1
✅ 결과
Q8_0 GGUF(4.1GB) 기반으로 정상 서빙을 확인하고, 1주 기한 안에 동작하는 서비스를 완성했습니다. Gemma가 system role을 지원하지 않아 시스템 프롬프트를 user 메시지에 합쳐 전달하도록 처리했습니다.
Learnings

배운 점

검색 품질은 모델보다 데이터와 인덱싱 방식(형태소 분석기, 하이브리드 가중치)이 먼저 좌우한다는 걸 하이브리드 검색을 튜닝하면서 체감했습니다.

모델별로 GGUF 변환 방식과 chat template, system role 지원 여부가 다 달라서, "GGUF를 실행 가능하게 만드는 것"과 "서비스에 쓸 품질을 확보하는 것"은 다른 문제라는 걸 배웠습니다.

가입 시 나이로 설명 난이도를 자동 설정하는 방식은 "나이가 많으면 법률 지식도 많다"는 전제가 깔려 있어 한계가 있습니다. 사용자가 직접 난이도를 선택하는 방식이 더 적절하다고 판단했고, 다음 개선 과제로 남겨뒀습니다.

현재 남아있는 한계로 대화 내역 미저장(세션 내에서만 유지), OpenSearch 보안 미설정(개발환경 한정), LLM 응답 지연을 스스로 인지하고 있고, 다음 단계로 개선하고 싶은 부분입니다.
