ApartTrade ETL — 서울 아파트 실거래가 증분 적재 시스템

2026.06.19 – 06.23 (5일, 1인 개발) · 기획·설계·구축·배포 전 과정 단독 수행
국토부 실거래 신고에는 최대 30일의 시차가 있어, 단순 1회 수집이 아닌 증분 수집·보정이 필요했습니다. 서울 25개구를 대상으로 아파트 실거래 ETL 파이프라인을 구축했습니다.
Overview

프로젝트 개요

dedup_key(8필드 조합) UNIQUE 제약 기반 증분 적재, 신고 지연 보정을 위한 이번달+지난달 매일 재조회, 단지 단위 평균 기반 이상거래 탐지를 핵심 설계로 삼았습니다.

Architecture

아키텍처

국토부 실거래 API │ (매일 이번달+지난달 재조회) ▼ Python ETL (쓰기 전용) │ ▼ MySQL (Docker) — dedup_key UNIQUE 제약으로 중복 방지 │ ▼ Spring Legacy (읽기 전용) │ ▼ JSP (Charts)

Python ETL(쓰기 전용)과 Spring Legacy(읽기 전용)를 DB로만 연결해 두 시스템이 서로 직접 호출하지 않도록 설계했습니다. 데이터 흐름을 처음 직접 설계해본 프로젝트로, 가장 단순하고 완전히 이해할 수 있는 구조를 택해 역할 분리를 명확히 하고 한쪽 장애가 다른 쪽에 영향을 주지 않도록 했습니다. 규모가 확장되면 Kafka/Airflow 등이 필요할 수 있다는 점도 인지하고 있습니다.

Problem Solving

문제 해결 과정

신고 지연 — 이번달 데이터가 왜 이렇게 적지?

문제
부동산 계약은 계약~신고까지 최대 30일의 시차가 있어, 당월에 한 번만 수집하면 실제 거래의 상당수가 누락됐습니다. (계약 당월 신고 1,349건 0.6% · 다음달 신고 10,098건 4.7% · 2달 이후 신고 205,015건 94.7%)
해결
매일 이번달+지난달을 함께 재조회하도록 스케줄을 설계하고, dedup_key UNIQUE 제약으로 재조회해도 중복 적재가 발생하지 않도록 했습니다.
결과
신고 지연으로 누락되던 거래를 빠짐없이 반영하는 증분 적재 구조를 완성했습니다.

이상거래 탐지 — 비교 기준이 잘못됐다

문제
구 단위 평균 ±30% 기준은 강남구처럼 초고가·중저가 단지가 혼재된 지역에서 고가 단지가 구조적으로 이상거래로 잡히는 문제가 있었습니다 (오탐 46,058건).
해결
비교 기준을 구 단위 평균에서 '같은 단지+같은 월 평균 평당가'로 변경하고, HAVING COUNT(*) >= 3으로 샘플 3건 미만 단지를 제외했습니다.
결과
오탐이 46,058건에서 496건으로 크게 줄었고, 결과를 직접 열어보니 직거래·급매·가족 간 거래로 추정되는 케이스가 실제로 포함되어 있어 '이상거래'에 걸맞는 결과로 개선됐습니다.

Learnings

배운 점

외부 API 데이터의 증분 적재 키를 직접 설계한 경험과, 신고 지연 같은 도메인 제약을 분석해 해결한 경험을 얻었습니다. 무엇보다 논리적으로 말이 되는 기준도 실제 데이터에서는 다른 결과를 낼 수 있다는 것, 그래서 결과가 이상하면 코드를 의심하기 전에 기준 자체가 맞는지 먼저 검증해야 한다는 점을 체감했습니다.
